# DEL & SHIP SYSTEM

*ERP System Documentation · System 5*

## 1. Purpose and System Scope

### 1.1 Purpose

The Del & Ship System is the ERP module responsible for preparing and tracking shipments after an order is approved for fulfillment. It records the recipient and delivery address, the items in a shipment, carrier and tracking details, shipment status, and status history. It provides a defined API so the Sales system and other ERP modules can exchange shipment information without directly editing Del & Ship’s tables.

In simple terms:

- **Order reference** = the Sales system’s order number, stored as a unique reference rather than a local Sales-order record.
- **Shipment** = the delivery work and recipient/address snapshot associated with one order.
- **Shipment item** = a description and quantity snapshot for an item being delivered; it is not a second Product record.
- **Shipment event** = a timestamped record of a shipment status change and its optional note.

### 1.2 Del & Ship responsibilities

- Create, view, search, and manage shipments.
- Store one or more item lines with each shipment.
- Track shipment preparation, dispatch, delivery, failure, and cancellation.
- Record status history and require a reason when a delivery attempt fails.
- Maintain carrier and tracking information separately from shipment status.
- Allow deletion only after a shipment is marked delivered.
- Read approved order details from the agreed Sales source and expose shipment APIs to other authorized systems.

### 1.3 User-facing functions

**Overview**

- Show shipment counts and operational summaries.
- Navigate to all shipments, in-transit shipments, delivery exceptions, and completed deliveries.

**Shipments**

- Create a shipment manually or look up a Sales order to prefill its recipient and item details.
- Search by order reference, recipient, carrier, or tracking number.
- Review the shipment’s items and event history.
- Update carrier and tracking number without changing status.

**Exceptions and completed deliveries**

- Record a delivery-failure reason and review it before arranging redelivery.
- Mark a delivered shipment for deletion only after an explicit confirmation in the user interface.

**Account and display**

- Sign in with a Django user account.
- Use the responsive mobile layout and light or dark appearance.
- The browser session expires after five minutes without activity.

### 1.4 System ownership boundary

Del & Ship owns shipment records, item snapshots, carrier/tracking details, statuses, and shipment events. It does **not** own Sales orders, buyer/customer records, product master data, stock levels, payment status, or courier networks. No separate buyer system is currently part of this module.

The `order_reference` is the link back to Sales. It is not a database foreign key. Customer and product identifiers returned by Sales are used for reference; the shipment stores only the fulfillment details needed to complete and track delivery. Del & Ship does not create or update records in Sales, Product, Inventory, or Finance tables.

## 2. Data Model

The following are the existing Del & Ship Django entities. Their records remain in the current shipment tables; the integration app adds no model, table, or migration.

### 2.1 `shipments_shipment`

| Field | Type | Constraint / purpose |
| --- | --- | --- |
| `id` | Big integer | Primary key generated by Django. |
| `order_reference` | `varchar(64)` | Required and unique; upstream Sales order number. |
| `recipient_name` | `varchar(180)` | Required recipient snapshot. |
| `delivery_address` | `text` | Required delivery-address snapshot. |
| `carrier` | `varchar(120)` | Optional carrier name. |
| `tracking_number` | `varchar(120)` | Optional tracking number; indexed for search. |
| `status` | `varchar(24)` | One of the defined shipment statuses; defaults to `ready_to_pack`. |
| `created_at` | datetime | Set when the shipment is created. |
| `updated_at` | datetime | Updated when the shipment changes. |

### 2.2 `shipments_shipmentitem`

| Field | Type | Constraint / purpose |
| --- | --- | --- |
| `id` | Big integer | Primary key generated by Django. |
| `shipment_id` | Big integer | Required foreign key to the shipment; item rows are deleted with their shipment. |
| `product_reference` | `varchar(64)` | Optional SKU or other source-system product reference. |
| `product_name` | `varchar(180)` | Required item-description snapshot. |
| `quantity` | positive integer | Required; must be at least 1. |

### 2.3 `shipments_shipmentevent`

| Field | Type | Constraint / purpose |
| --- | --- | --- |
| `id` | Big integer | Primary key generated by Django. |
| `shipment_id` | Big integer | Required foreign key to the shipment; events are deleted with their shipment. |
| `status` | `varchar(24)` | Status reached by this event. |
| `note` | `varchar(240)` | Optional event note; required when the status becomes `delivery_failed`. |
| `occurred_at` | datetime | Set when the event is recorded. |

Creating a shipment also creates its first event. Later valid status changes add events; the event history is returned with shipment details.

### 2.4 Relationships and ownership

- One shipment has one or more shipment-item rows.
- One shipment has one or more shipment-event rows.
- Item and event rows use a cascading foreign key to their Del & Ship shipment.
- A shipment has one unique `order_reference`; split or partial shipments for one order are not currently supported.
- Sales, customer, and product records remain owned by their source systems and are not linked through local foreign keys.

## 3. Business Rules

### 3.1 Shipment status flow

| Current status | Allowed next status |
| --- | --- |
| `ready_to_pack` | `packing`, `cancelled` |
| `packing` | `ready_to_dispatch`, `cancelled` |
| `ready_to_dispatch` | `in_transit`, `cancelled` |
| `in_transit` | `delivered`, `delivery_failed` |
| `delivery_failed` | `in_transit` for redelivery, `cancelled` |
| `delivered` | No further status change. |
| `cancelled` | No further status change. |

The backend validates every transition. A failed delivery must include a reason of 240 characters or fewer. The next redelivery attempt moves the shipment from `delivery_failed` to `in_transit` and creates a new event.

### 3.2 Shipment and edit rules

- A shipment must have a unique order reference, recipient, delivery address, and at least one item line.
- Every shipment-item quantity must be a positive whole number.
- Carrier and tracking details can be changed only through the dedicated logistics endpoint. Generic shipment `PATCH` is disabled.
- A shipment can be permanently deleted only when its status is `delivered`. Its items and event history are deleted with it.
- An integration retry with an already-used `order_reference` returns the existing shipment and does not overwrite it. The first accepted snapshot remains authoritative in Del & Ship.
- The source Sales status is returned for review, but Del & Ship does not decide whether an order has passed payment, inventory, or other fulfillment checks.

## 4. Integration Requirements

### 4.1 Integration principle

Other ERP modules should exchange data through the documented API and stable business references. The current Sales lookup uses parameterized, read-only queries through Del & Ship’s configured default database connection. It does not write to the Sales or Product tables and it creates no second copy of those master records.

If Sales is deployed in a separate database or service, keep the normalized order response below and replace the table adapter with an agreed Sales API or read-only database connection. Do not let each module edit another module’s private tables.

### 4.2 Data read from Sales

The supplied schema defines these source fields for the current lookup:

| Source table | Fields read | Use in Del & Ship |
| --- | --- | --- |
| `sales_salesorder` | `id`, `order_number`, `status`, `order_date`, `customer_id` | Order reference, source status, and order timestamp. |
| `sales_customer` | `id`, `customer_code`, `customer_name`, `address` | Source identifiers and recipient/address snapshots. |
| `sales_salesorderitem` | `id`, `sales_order_id`, `product_id`, `quantity` | Order item reference and quantity. |
| `catalog_product` | `id`, `sku`, `name` | Product reference and item-description snapshot. |

The lookup does not copy email, phone, prices, payments, or inventory balances. The supplied schema has no order-level ship-to address, so the current mapping uses `sales_customer.address`. If an order can be delivered somewhere else, the Sales contract needs an order-level address before this lookup is suitable for real fulfillment.

The current MySQL database contains Del & Ship’s shipment tables and `catalog_product`, but it does not contain `sales_salesorder`, `sales_salesorderitem`, or `sales_customer`. Sales order lookup therefore returns HTTP 503 until those source tables are available in the configured database. The supplied SQL file defines a complete schema for a new or empty database and does not seed actual Sales orders or customers. **Do not run it against the current database:** it also defines legacy `delivery_*` tables, while this application uses its existing `shipments_*` models. No database changes were made for this integration.

### 4.3 Data exchanged with other systems

**Sales to Del & Ship:** an authorized user can retrieve a Sales order for review and prefill a new shipment. An upstream server can also submit a fulfillment snapshot after its own order-eligibility checks have passed.

**Del & Ship to other systems:** an authorized caller can retrieve the current shipment status, carrier, tracking number, items, and event history. The current integration supports polling; it does not send event webhooks or callbacks.

### 4.4 Suggested API endpoints

Local API base URL: `http://127.0.0.1:8238/api/`. Normal shipment routes use the logged-in Django session. Integration routes accept that session for the Del & Ship UI or the server-to-server key described in Section 5.

| Method | Endpoint | Purpose |
| --- | --- | --- |
| GET | `/shipments/` | List shipments; supports `?status=in_transit`, `?search=SO-10042`, and page-size controls. |
| POST | `/shipments/` | Create a shipment with one or more item snapshots. Initial status is `ready_to_pack`. |
| GET | `/shipments/{id}/` | Retrieve shipment, items, and event history. |
| POST | `/shipments/{id}/status/` | Apply a validated status transition and record its note. |
| PATCH | `/shipments/{id}/logistics/` | Update only `carrier` and/or `tracking_number`. |
| DELETE | `/shipments/{id}/` | Delete only a delivered shipment and its dependent item/event records. |
| GET | `/integrations/sales-orders/{order_number}/` | Read and normalize one Sales order; does not create a shipment. |
| POST | `/integrations/shipments/` | Receive an upstream shipment snapshot; duplicate references return the existing record. |
| GET | `/integrations/shipments/{order_reference}/` | Poll one shipment and its event history. |

Example inbound shipment request:

```json
{
  "order_reference": "SO-10042",
  "recipient_name": "Sample Customer",
  "delivery_address": "Campus address",
  "carrier": "",
  "tracking_number": "",
  "items": [
    {"product_reference": "SKU-012", "product_name": "Sample product", "quantity": 2}
  ]
}
```

The first accepted request returns HTTP 201. A retry using the same `order_reference` returns HTTP 200 and the existing shipment without changing it. Call the shipment detail endpoint to retrieve its current status and history.

### 4.5 Integration safeguards

- Use the order number as a stable unique reference; prefix it with the source-system name if references may overlap across systems.
- Send only orders that meet the agreed fulfillment-eligibility rules. Those rules must be owned by Sales or the upstream workflow, not inferred from a displayed status.
- Validate required recipient, address, item, and quantity fields before accepting a shipment.
- Keep API keys on trusted backend services and use HTTPS when requests leave localhost.
- Agree whether consumers will poll status or need a future webhook/event mechanism.

## 5. Assumptions and Items Requiring Team Confirmation

- **Order eligibility:** confirm which Sales status and business checks allow fulfillment. The current module does not verify payment or reserve stock.
- **Ship-to address:** confirm whether the customer’s saved address is sufficient or whether Sales must provide an order-level delivery address.
- **Shipment cardinality:** confirm that one order always produces one shipment. Split shipments and partial fulfillment are not implemented.
- **Database ownership:** confirm that the Sales source tables will be created in the configured shared database. If not, provide a Sales API or approve a read-only source connection.
- **Authentication:** `ERP_INTEGRATION_API_KEY` is blank by default. External callers cannot use the key until the project owner configures it in the private backend environment.
- **Permissions:** the current classroom implementation protects routes by login or integration key but does not define detailed staff roles for shipment actions.
- **Privacy and deployment:** order lookups return recipient name and address. Limit callers to the required systems and do not expose the integration key or customer data in browser code or public logs.

For local server-to-server testing, generate a key with:

```powershell
python -c "import secrets; print(secrets.token_urlsafe(32))"
```

Set the result as `ERP_INTEGRATION_API_KEY` in `backend/.env`. Do not commit that value. The browser continues to use the existing Django session and CSRF flow; it does not use or store this integration key. Django’s session cookie is HttpOnly and expires after five minutes of inactivity in the frontend. The current security settings are for a classroom/local demonstration; configure HTTPS, secrets, and stronger permissions before public deployment.
